# Backend shape on Cloudflare

Answers [issue #5](https://github.com/Today20092/cutnotes/issues/5). Researched 2026-11-08 from vendor docs and vendor source code. Nothing here was built or run; see [What could not be confirmed](#what-could-not-be-confirmed).

## Recommendation

Build one Cloudflare Worker running **TanStack Start with server-side rendering of routes turned off**, on the **Workers Paid plan ($5 a month)**.

| Area | Choice |
| --- | --- |
| Framework | TanStack Start on `@cloudflare/vite-plugin`, with `defaultSsr: false` |
| Database access | Drizzle ORM over the D1 binding, each screen's reads in one `db.batch()` |
| Migrations | Generated by `drizzle-kit generate`, applied by `wrangler d1 migrations apply` |
| Auth | `@clerk/tanstack-react-start` `clerkMiddleware()` with `CLERK_JWT_KEY` set, plus a fresh token sent on every server call |
| Scheduled deletion | One hourly Cron Trigger on the same Worker |
| Client data | TanStack Query: optimistic mutations, 30-second polling on the Video screen only |
| Database location | `--location` hint nearest the team; read replication off |

Why this shape serves speed:

- After the first load, every tap is handled in the browser from the Query cache. The network only confirms it. Backend latency therefore affects freshness, not how fast a tap feels.
- With route SSR off, a page load runs no database query before HTML is returned. The browser then asks for the data in one call.
- The real backend cost is round trips to D1, because a Worker runs near the user while the D1 primary sits in one place. One batch per screen makes that a single trip.

Package versions current on npm on the research date: `@tanstack/react-start` 1.169.5, `@clerk/tanstack-react-start` 1.7.11, `drizzle-orm` 0.45.4, `wrangler` 4.158.0, `@tanstack/react-query` 5.107.1.

## Web framework: TanStack Start

- It is officially supported on both sides. Cloudflare has a [framework guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/tanstack-start/) and lists it as officially supported by the [Vite plugin](https://developers.cloudflare.com/workers/vite-plugin/). Clerk has a [first-party quickstart](https://github.com/clerk/clerk-docs/blob/main/docs/getting-started/quickstart.tanstack-react-start.mdx). TanStack documents [Cloudflare hosting](https://tanstack.com/start/latest/docs/framework/react/guide/hosting).
- Lawn, the candidate reference code, already uses TanStack Start (its `app/routes/` tree), which helps ticket #6.
- A custom server entry exports `fetch` and `scheduled` together, so the app and the deletion job are one Worker and one deploy ([guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/tanstack-start/)).
- D1 is reached with `import { env } from "cloudflare:workers"` inside server functions (same guide).
- Set `defaultSsr: false` in `createStart` ([selective SSR](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr)). The HTML shell is still produced by the Worker, while loaders and components run in the browser.
- Keep full SPA mode as a later option only. A static shell would skip the Worker on page load, but Clerk's handshake runs in middleware on document requests (see below), and Clerk's docs do not cover that setup.

Rejected: a separate Hono API with a Vite SPA works, but means two pieces to wire and no first-party Clerk integration for the pair. Next.js on Workers needs vinext or OpenNext, which adds a layer this app does not need.

## D1 access and migrations

**Access.** Use Drizzle's D1 driver for typed queries. Its [`db.batch()`](https://orm.drizzle.team/docs/latest-releases/drizzle-orm-v0290) maps to D1's batch and returns typed results for each statement.

**Migrations.**

1. `drizzle-kit generate` writes SQL from the schema. It needs no Cloudflare credentials; Drizzle's [config docs](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/sqlite/drizzle-config-file.mdx) list the `d1-http` driver only for `push`, `migrate`, `pull` and `studio`.
2. `wrangler d1 migrations apply DB --remote` applies them and records them in `d1_migrations` ([docs](https://developers.cloudflare.com/d1/reference/migrations/)).
3. If the pinned drizzle-kit writes nested folders, set `migrations_dir` and `migrations_pattern` ([docs](https://developers.cloudflare.com/d1/reference/migrations/#nested-migration-layouts)).

**Useful D1 facts** ([limits](https://developers.cloudflare.com/d1/platform/limits/) unless noted):

- Foreign keys are [enforced by default](https://developers.cloudflare.com/d1/sql-api/foreign-keys/), so `ON DELETE CASCADE` can do the row cleanup.
- Time Travel restore is [always on](https://developers.cloudflare.com/d1/reference/time-travel/), reaching 30 days back on Paid. That covers accidental deletion with no backup setup.
- Maximum 10 GB per database on Paid, and 100 bound parameters per query, so bulk inserts must be chunked.

**Location.** Create the database with `wrangler d1 create cutnotes --location=<hint>`. The hint is a [preference, not a guarantee](https://developers.cloudflare.com/d1/configuration/data-location/). D1 does not run in South America, Africa or the Middle East, so a team there should pick the nearest supported region.

**Leave read replication off.** It still requires the Sessions API and bookmark handling on every request ([docs](https://developers.cloudflare.com/d1/best-practices/read-replication/)), and a single small team gains little. Writes always go to the primary anyway. Turn it on only if measured reads are slow for people far from the primary.

**Leave Worker placement at the default.** Smart Placement [needs consistent traffic from multiple locations](https://developers.cloudflare.com/workers/configuration/smart-placement/), which under 10 people will not produce. Placement Hints take [cloud regions or probeable hosts](https://developers.cloudflare.com/workers/configuration/placement/), and D1 is neither. One batch per screen removes most of what placement would save.

## Transaction limits

- `db.batch()` is the transaction tool. Statements run in order, and a failure [rolls back the whole sequence](https://developers.cloudflare.com/d1/worker-api/d1-database/).
- A batch cannot read a value, run JavaScript on it, then continue. Put the decision in SQL. For a single-use invite, in one batch:
  1. `INSERT INTO members ... SELECT ... FROM invites WHERE token = ? AND used_at IS NULL AND expires_at > ?`
  2. `UPDATE invites SET used_at = ? WHERE token = ? AND used_at IS NULL`

  Check the `changes` count on the insert to tell the user whether it worked.
- The whole batch must finish in [30 seconds](https://developers.cloudflare.com/d1/platform/limits/). Each statement is limited to 100 KB.
- A Worker invocation can make 1,000 queries on Paid, and a batch [counts as one](https://developers.cloudflare.com/d1/platform/limits/).
- Each database [handles one query at a time](https://developers.cloudflare.com/d1/platform/limits/). Indexed reads take [under a millisecond](https://developers.cloudflare.com/d1/platform/limits/), so this team will not queue. Long bulk deletes are the one risk, so they are chunked (below).

## Clerk session verification

- Add `clerkMiddleware()` to `requestMiddleware` in `src/start.ts`. Creating that file removes TanStack's default CSRF protection, so **`createCsrfMiddleware` must be added explicitly** ([Clerk docs](https://github.com/clerk/clerk-docs/blob/main/docs/reference/tanstack-react-start/clerk-middleware.mdx)).
- The middleware does not protect anything by itself. All routes are public until checked, so every server function needs its own check ([same docs](https://github.com/clerk/clerk-docs/blob/main/docs/getting-started/quickstart.tanstack-react-start.mdx)).
- Set `CLERK_JWT_KEY` so verification is [networkless](https://github.com/clerk/clerk-docs/blob/main/clerk-typedoc/backend/verify-token.mdx); without it Clerk fetches its keys over the network. Clerk's middleware [reads this variable](https://github.com/clerk/javascript/blob/main/packages/tanstack-react-start/src/server/loadOptions.ts).
- Set `authorizedParties` to the app's own origin. Clerk warns that [omitting it can open CSRF attacks](https://clerk.com/docs/guides/sessions/manual-jwt-verification).
- Secrets reach Clerk through `process.env`, which Workers [populates](https://developers.cloudflare.com/workers/configuration/compatibility-flags/) with `nodejs_compat` on a compatibility date of 2025-04-01 or later.

**Phones waking up need one addition.** Clerk tokens [last 60 seconds and refresh every 50](https://clerk.com/docs/guides/how-clerk-works/overview). A phone returning from the background can send an expired cookie. Clerk's automatic recovery, the [handshake](https://github.com/clerk/javascript/blob/main/packages/backend/src/tokens/handshake.ts), only runs for page navigations, not data calls. Reading that source, a server function call with an expired cookie looks signed out, which would show an error on the exact "return to the app" moment the spec cares about.

The fix is a [client middleware](https://tanstack.com/start/latest/docs/framework/react/guide/middleware) on every server function that awaits Clerk's `getToken()` and sends `Authorization: Bearer <token>`. Clerk's [request handling](https://github.com/clerk/javascript/blob/main/packages/backend/src/tokens/request.ts) accepts header tokens. The first build ticket should test this on a real phone.

**Permissions.** Clerk proves who the person is. Role, membership and Share Link rules live in D1. Read the member row in the same batch as the screen's data, so authorization costs no extra round trip.

## Scheduled deletion

Use one hourly Cron Trigger (`0 * * * *`) with a `scheduled()` handler in the custom server entry. Cloudflare Workflows would add durable steps this job does not need.

1. Completing a Project stores `delete_after` (now plus 14 days). Reopening clears it.
2. Each run finds due Projects with an indexed query.
3. For each Video, delete the Mux asset first, treating "already gone" as success. Then delete the database rows.
4. Delete in chunks of about 1,000 rows, as [Cloudflare advises](https://developers.cloudflare.com/d1/platform/limits/). The next run continues any unfinished work.

Every step must be safe to repeat. Cloudflare's own [cron example](https://developers.cloudflare.com/containers/examples/cron/) says to make tasks idempotent because exactly-once execution is not guaranteed.

Hourly means a failed run costs an hour. An interval of an hour or more also gets the [15-minute CPU allowance](https://developers.cloudflare.com/workers/platform/limits/), where shorter intervals get 30 seconds. Cron runs on [UTC](https://developers.cloudflare.com/workers/configuration/cron-triggers/), and wall time is [limited to 15 minutes](https://developers.cloudflare.com/workers/platform/limits/).

## Optimistic updates with periodic refresh

Use the [TanStack Query optimistic pattern](https://github.com/TanStack/query/blob/main/docs/framework/react/guides/optimistic-updates.md): in `onMutate` cancel running fetches, snapshot, and write to the cache; in `onError` restore; in `onSettled` invalidate. Integrate it with the router as [TanStack Start documents](https://tanstack.com/start/latest/docs/framework/react/guide/tanstack-query), with `staleTime: 30_000` and `defaultPreload: 'intent'`.

Rules for this app:

- **The browser generates IDs** for Comments and Drawings, and the server uses `INSERT ... ON CONFLICT DO NOTHING`. A retry can then never create a duplicate, and the optimistic row keeps its identity when real data arrives.
- **Serialize writes per Video** with a shared [`scope.id`](https://github.com/TanStack/query/blob/main/docs/framework/react/guides/mutations.md). Mutations otherwise run in parallel and could land out of order.
- **Only the last pending mutation invalidates**, by checking `isMutating`, so one finishing write does not refetch over another still pending.
- **Poll only on the Video screen**, with `refetchInterval: 30_000`. Background polling is [off by default](https://github.com/TanStack/query/blob/main/packages/query-core/src/types.ts), which matches "while a Video is open". Refresh on return with `refetchOnWindowFocus`.
- **Deleted Comments** must disappear for others, so the poll should return the whole Revision's Comments rather than only changes. At this size that is cheap and avoids sync bugs.

No Durable Objects, WebSockets or queues are needed.

## Cloudflare plan: Workers Paid

Pay the [$5 a month](https://developers.cloudflare.com/workers/platform/pricing/). Usage is not the reason. The Free plan's hard limits are:

- **CPU.** Free allows [10 ms per request](https://developers.cloudflare.com/workers/platform/limits/). Cloudflare says [auth or SSR workloads typically use 10 to 20 ms](https://developers.cloudflare.com/workers/platform/limits/) and that [SSR apps usually need Paid](https://developers.cloudflare.com/workers/static-assets/migration-guides/vercel-to-workers/). Random CPU-limit failures are the worst outcome for a speed-first app.
- **Deletion job.** Free allows [50 external calls per invocation](https://developers.cloudflare.com/workers/platform/limits/) and 10 ms of cron CPU. Paid allows 10,000 calls.
- **Failure mode.** Since 2026-09-01, D1 on Free [returns errors until midnight UTC](https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/) once a daily limit is hit.

Estimated volume (my arithmetic, assumptions stated): 10 people with a Video open 8 hours a day each, polling every 30 seconds, is at most 9,600 requests a day. At 300 rows per poll that is about 2.9 million rows read a day, or about 86 million a month.

[Paid includes](https://developers.cloudflare.com/d1/platform/pricing/) 25 billion rows read and 50 million written a month, 5 GB of storage, and [10 million requests](https://developers.cloudflare.com/workers/platform/pricing/). Expect no overage. [Static assets are free](https://developers.cloudflare.com/workers/platform/pricing/). Video never touches Cloudflare.

Clerk's [Hobby plan](https://clerk.com/pricing) is free up to 50,000 monthly retained users and lists Google sign-in, email codes and custom domains.

## Setup for the agent guide

One script, in this order. Agents write it; the human runs the production steps.

1. Commit a complete `wrangler.jsonc` with `nodejs_compat`, the D1 binding and the cron. Without a config file, `wrangler deploy` [auto-configures the project](https://developers.cloudflare.com/workers/framework-guides/web-apps/tanstack-start/), which should be avoided.
2. `wrangler d1 create cutnotes --location=<hint>`, then write the ID into the config. Prefer this to [automatic provisioning](https://developers.cloudflare.com/workers/wrangler/configuration/#automatic-provisioning), which launched as an [open beta](https://developers.cloudflare.com/changelog/post/2025-10-24-automatic-resource-provisioning/) and shows no way to pass a location.
3. `wrangler secret put` for the Clerk and Mux values. Only Clerk's publishable key is needed at build time.
4. `wrangler d1 migrations apply DB --remote`.
5. `wrangler deploy`.

Use Wrangler rather than the newer `cf` CLI, which [Cloudflare still labels beta](https://developers.cloudflare.com/cf/wrangler/migrate/).

## What could not be confirmed

Nothing was prototyped or deployed, so all of this rests on documents and source reading.

- **No latency was measured.** The claim that one batch per screen is enough is reasoning, not a benchmark. The real numbers for the team's location are unknown.
- **The team's location is unknown to this research.** The `--location` value is a setup input, and users in the Middle East, Africa or South America would have a farther primary.
- **The expired-cookie behaviour** comes from reading Clerk's source, not from a test or a doc statement. The Bearer-token fix is likewise untested with `@clerk/tanstack-react-start`.
- **Clerk with `defaultSsr: false`** is built from separate docs. Neither vendor documents the combination.
- **`CLERK_JWT_KEY` on Workers** was traced through source to `process.env`, but not run.
- **`BEGIN TRANSACTION` support.** The D1 pages read neither allow nor forbid it. This design does not use it; it relies only on `batch()`.
- **Cron retries.** Cloudflare's docs show a `noRetry()` method but the pages read do not state when failed runs retry. The design assumes nothing and is safe to repeat.
- **Actual CPU use per request** for this app was not measured, so the Free plan is ruled out on Cloudflare's typical figures and the deletion limit, not on a test.
- **Clerk Hobby on a production instance.** The pricing page lists the features but does not explicitly say a production instance is included.
- **drizzle-kit's folder layout** at the pinned version was not checked. Drizzle is also pre-1.0, so pin the version.
- **Mux delete behaviour and rate limits** belong to ticket #4 and are not covered here.
